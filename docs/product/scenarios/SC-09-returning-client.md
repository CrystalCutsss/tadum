# SC-09 · Повторный клиент

| Поле | Значение |
|---|---|
| **ID** | `SC-09` |
| **Роли** | `client_contact`, `client_owner`, `unknown` |
| **Экраны** | `auth.phone`, `auth.otp`, `client.home`, `client.closed`, `client.reapply`, лендинг (вне портала) |
| **Предусловие** | У номера телефона уже есть заявка (активная или закрытая), и клиент пытается подать новую или снова входит |
| **Статусы** | Любые; ключевое правило — **1 телефон = 1 активная заявка = 1 кабинет** (`01-roles.md` §2) |
| **Цель** | Клиент с активной заявкой никогда не создаёт дубль — любая попытка «подать заявку» приводит его в существующий кабинет; клиент с закрытой заявкой может подать новую |
| **Метрика** | Доля попыток повторной подачи при активной заявке, завершившихся входом в кабинет (дубликаты в Odoo → 0); доля закрытых, подавших новую заявку |
| **Версия прототипа** | v4 (логика входа — v1) |
| **Персоны мока** | `client_partial` (активная заявка), `client_closed_lost` (закрытая), `unknown_phone` |
| **Связанные документы** | `01-roles.md` §2–3, `01-statuses.md` §9 (повторная заявка), `SC-01`, `SC-08` |
| **Статус** | черновик — живой каркас (вопросы закрыты) |

---

## 1. Основной сценарий

```
Дано:  у номера есть активная заявка (client_status ∈ {docs_required, under_review, approved, first_purchase})
Когда: клиент на лендинге нажимает «Подать заявку» и вводит этот номер (форма лендинга — вне портала)
Тогда: лендинг (бэкенд) определяет, что активная заявка есть, и вместо создания новой
       перенаправляет на /login?returnTo=/c/home&src=landing&lang=… портала (D-039);
       клиент проходит OTP (SC-01) и попадает в существующий кабинет — обычный home с заявкой и её
       статусом; отдельного экрана или баннера «у вас уже есть заявка» нет (D-040);
       событие returning_redirected_to_cabinet {from: landing}

Дано:  у номера только закрытая заявка (client_status = closed)
Когда: клиент входит в портал
Тогда: экран client.closed (SC-08) с кнопкой «Подать новую заявку» → /c/reapply (D-038);
       после «Создать заявку» появляется новая заявка → обычный кабинет (SC-02)

Дано:  клиент с активной заявкой открывает портал напрямую (не через лендинг)
Когда: проходит вход
Тогда: обычный SC-01 — кабинет существующей заявки; никаких дополнительных экранов
```

Граница ответственности: первичную заявку создаёт лендинг; дедупликация по номеру до создания заявки выполняется на стороне лендинга/бэкенда (Odoo) и обязательна (D-039). Портал создаёт заявку только в одном случае — повторную, со страницы `/c/reapply` при закрытой предыдущей (D-038). Повторный клиент с активной заявкой просто видит свою заявку и её статус — без дополнительных экранов и баннеров (D-040).

## 2. Альтернативные сценарии и ошибки

| # | Условие | Что видит (ключ) | Действие | Событие |
|---|---|---|---|---|
| A1 | У номера две активные заявки (ошибка данных) | Кабинет последней по дате; баннера нет; событие для команды | — | `auth_multiple_applications_detected` |
| A2 | Клиент — `client_owner` одной заявки и `client_contact` другой компании | В MVP — одна активная заявка на номер; показываем последнюю по дате, остальное — вне MVP (D-010) | — | `auth_multiple_applications_detected` |
| A3 | Закрытая заявка, клиент пришёл по старой WhatsApp-ссылке на `/c/documents` | После входа — `/c/closed` (гард), документы доступны для чтения | — | — |
| A4 | Новая заявка создана через `/c/reapply`, но Odoo ещё не обработал (несколько минут) | После нажатия показываем `reapply.submitting`, затем `home` новой заявки из ответа порта; если данных ещё нет — `client.closed` остаётся с подписью `reapply.pending` | повторить позже | `reapply_pending_viewed` |
| A5 | Номер без заявок вообще | `auth.not_found` (SC-01 A8) → «Подать заявку» → лендинг | — | `auth_otp_failed {reason: phone_unknown}` |
| A7 | Лендинг не смог проверить дубль (ошибка) и создал вторую заявку | Портал ведёт себя как A1; дубли разбирает команда в Odoo | — | `auth_multiple_applications_detected` |

## 6. Критерии приёмки

- [ ] Первичную заявку портал не создаёт; «Подать заявку» для `unknown` ведёт на лендинг с `?lang=`. Повторную заявку создаёт только `/c/reapply` при закрытой предыдущей (D-038).
- [ ] Клиент с активной заявкой после входа всегда попадает в существующий кабинет и видит заявку со статусом; никаких дополнительных экранов и баннеров (D-040).
- [ ] Клиент с закрытой заявкой видит `client.closed` → `/c/reapply` → после создания новой заявки кабинет переключается на неё без участия поддержки.
- [ ] Несколько активных заявок не ломают вход: берётся последняя, событие отправлено.
- [ ] Признак перенаправления с лендинга (`?src=landing`) используется только для аналитики, не для UI; передаётся без PII.
- [ ] Тексты в `ar` и `en`; баннер доступен и закрывается с клавиатуры.
- [ ] Storybook: `client.reapply` stub / submitting; `client.closed` reapply-pending × AR/EN × light/dark.
- [ ] Playwright: вход `client_partial` с `?src=landing` → обычный `home`, событие отправлено; `client_closed_lost` → `/c/closed` → `/c/reapply` → «Создать заявку» → `/c/home` новой заявки.

## 7. Заметки для реализации

- Параметр `?src=landing` читается один раз при входе, уходит в событие аналитики и убирается из URL; на UI не влияет.
- Логика «последняя по дате» живёт в `resolveRoles` (мок) и должна совпасть с бэкендом — зафиксировать в контракте портов.
- Мок: `createApplication()` для `client_closed_lost` создаёт заявку `docs_required` с пустым комплектом; задержка 2 с для состояния `submitting`; демо-панель умеет имитировать A4 (задержка ответа Odoo).

## 8. Открытые вопросы

Решено (Кирилл, 2026-11-04): SC9-1 — лендинг обязан проверять дубль по номеру до создания заявки и передавать клиента в портал редиректом на `/login?returnTo=/c/home&src=landing&lang=…` (D-039). SC9-2 — ни экрана, ни баннера «у вас уже есть заявка»: повторный клиент просто видит свою заявку со статусом (D-040).

Открытых вопросов по сценарию нет.
