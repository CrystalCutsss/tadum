## 0. Зачем этот документ и как им пользоваться

Цель — за две фазы получить среду, в которой Claude Code месяцами собирает прототип личных кабинетов Tadum (клиент + поставщик), не разваливая уже написанное, а команда смотрит версии на витрине Proto по паролю. Бэкенда нет; после прототипа репозиторий уедет из GitHub в GitLab команды разработки, где к нему подключат бэкенд (Odoo).

Документ отвечает на три вопроса: **что** делаем (разделы 2–3), **в каком порядке** (раздел 4) и **что ещё надо решить** (раздел 5). Каждый пункт плана заканчивается «Результатом» — конкретным файлом в Drive или в репозитории — и критерием готовности. Пункты, помеченные ⚖️, содержат варианты, по которым нужно выбрать; пункты с ❓ — открытые вопросы, вынесенные в раздел 5.

Принципы, которые действуют на всём протяжении проекта:

1. **Google Drive `Tadum/` — источник правды по продукту.** Вся продуктовая документация пишется на русском и лежит там. В репозитории лежит только документация для разработки и снимки (копии) продуктовых документов, которые читают агенты.
2. **Требования пишем в форматах, пригодных для кода** (таблицы со стабильными идентификаторами, YAML/TS-подобные описания сущностей, сценарии в формате «дано / когда / тогда»), чтобы агент мог превратить их в типы, фикстуры и тесты без переосмысления.
3. **Агент не должен угадывать.** Всё, что можно проверить машиной (типы, линтер, тесты, скриншоты RTL/LTR, паритет ключей AR/EN), проверяется машиной в хуках и CI; CLAUDE.md только объясняет, хуки — запрещают.
4. **Одна фича — один бриф — одна ветка — один PR.** Маленькие изменения, видимый результат на витрине после каждого PR.

#### Аналитика и метрики

Главная метрика продукта — **O3 KR3: конверсия Doc collection → Assessed с 0,7–5,7 % до 20 %** (клиент). Для поставщика — доля приводящих поставщиков, заходящих в кабинет ≥ 1 раза в месяц, и O1 KR2 (assessed leads от малых поставщиков 12 → 30 / 70 / 150).

Что делаем в фазе 1 (документ `04 Аналитика и метрики/04-metrics-and-events.md`):

1. Дерево метрик: главная метрика → промежуточные (доля заявок с полным комплектом за 12 часов, среднее число перезагрузок документа, доля отклонённых документов, повторно загруженных в течение 24 часов, доля входов из WhatsApp) → события.
2. **Словарь событий** в формате таблицы со стабильными именами в `snake_case`, обязательными свойствами и моментом срабатывания. Стартовый набор из требований: `auth_otp_requested`, `auth_otp_failed {reason}`, `auth_login_succeeded {role}`, `role_switched`, `language_changed {to}`, `document_upload_started/succeeded/failed {portal_key, reason}`, `document_prevalidation_failed {portal_key, rule}`, `document_set_submitted`, `rejected_document_reuploaded`, `support_contact_clicked {channel}`, `referral_link_copied`, `referral_shared_whatsapp`, `referral_qr_downloaded`, `material_downloaded {id, lang}`, `clients_list_opened`, `checklist_link_opened {item}`.
3. В коде — модуль `src/shared/analytics/` с типом `AnalyticsEvent` (discriminated union, генерируется из словаря) и функцией `track()`. Пока единственный провайдер — `ConsoleProvider` (и панель событий в демо-режиме); боевой провайдер выбирается в SFL-895, предпочтительный кандидат — PostHog (события, флаги и записи сессий в одном инструменте), словарь событий проектируем совместимым с ним.
4. Правило DoD: каждая фича объявляет свои события в брифе, а PR не принимается без их вызова на успешном и на ошибочном пути.

### 2.3 Требования: языки и рынки, нефункциональные, бренд и TOV

Один документ `01 Требования к продукту/01-nfr-locale-brand.md` с тремя разделами. Основа уже есть в требованиях клиента; ниже — что нужно дополнить, чтобы агенту хватало для кода.

**Языки и рынки.** Рынок только KSA. Арабский по умолчанию, `?lang=` из WhatsApp-ссылки, выбор хранится в браузере. RTL зеркальный, включая стрелки и шкалу прогресса; не зеркалим нейтральные иконки (часы, телефон, логотип). Цифры западные 0–9 в обоих языках → везде `numberingSystem: 'latn'`. Телефон `+966 5X XXX XXXX` как изолированный LTR-фрагмент (`<bdi dir="ltr">`). Валюта: «SAR» в английском интерфейсе, «ر.س» в арабском — переключается вместе с языком (решено). Даты — григорианские принудительно (`ar-SA-u-ca-gregory-nu-latn`, иначе движок может подставить хиджру), хиджра не показывается (решено); формат `DD/MM/YYYY` в обоих языках, пока не решено иначе. Часовой пояс Asia/Riyadh. Добавить: правило длины текста (арабский в среднем на 20–25 % длиннее), словарь терминов AR/EN (лимит, комплект документов, статусы), правила транслитерации названий компаний.

**Нефункциональные требования.** Mobile-first: базовый макет 360 px, контрольные точки 360 / 768 / 1280. Браузеры: iOS Safari, Android Chrome, встроенный браузер WhatsApp (ключевой), десктопные Chrome / Safari / Edge (две последние версии). Сессия сохраняется после перезагрузки и в новой вкладке, выход работает; «помнить меня» 30 дней, таймаута неактивности в MVP нет (решено). Файлы PDF / JPG / PNG до 10 МБ с прогрессом загрузки. Добавить: производительность (LCP ≤ 2,5 с на 4G, бюджет первого чанка ≤ 200 КБ gzip), доступность WCAG 2.2 AA (контраст, фокус, цели касания ≥ 44 px, подписи у полей), PWA (манифест с `dir: rtl`, `lang: ar`, установка на домашний экран; офлайн — только состояние «нет сети», не оффлайн-работа), ограничения WhatsApp in-app browser (скачивание файлов через прямые URL с `Content-Disposition`, подсказка «открыть в браузере», отдельное хранилище → сессия может не переноситься), безопасность клиента (нет PII в URL и аналитике, маскирование телефона).

**Бренд и TOV.** Из требований: тон спокойный, уважительный, «персональный менеджер»; одна мысль на экран; запрет слов «кредит», «заём», «финансирование», «процент», «BNPL», обещаний сроков и «мгновенного одобрения»; третьи стороны (Sadq, Nafith, ZATCA, WhatsApp) только текстом. Разрешено: «торговый лимит», «купите сейчас — платите частями», «Tadum покупает товар у вашего поставщика», «первоначальный ответ». Добавить: регистр арабского — формальный MSA, обращение на «вы» (решено), правила для ошибок (что произошло → что сделать → куда обратиться), правила для пустых состояний, шаблоны статусных текстов «на чьей стороне шаг», глоссарий запрещённых/разрешённых формулировок на обоих языках как машиночитаемый список (`tov-lexicon.json`) — его будет проверять скилл `ux-writer` и линтер текстов.

**Результат:** `01-nfr-locale-brand.md` + `tov-lexicon.json`. Критерий готовности: все решения Р13 перенесены в документ, ни одного открытого вопроса без владельца.

Роли: `client_contact` (контактное лицо заявки), `client_owner` (основной владелец), `supplier`, `dual` (один телефон с обеими ролями), `unknown` (номер без заявки). Отдельно — матрица прав клиента по четырём состояниям заявки (из требований) и матрица поставщика (ссылка всегда активна; документы по тем же правилам; что скрыто: телефон клиента, лимит, причина закрытия). Служебные роли (Sales, UW, Ops) описываются одной строкой: «работают в Odoo, в портале не присутствуют». Один пользователь на компанию (решено); несколько пользователей (бухгалтер) — вне MVP.

#### Структура кабинета — `01-cabinet-structure.md`

Одна оболочка на две роли. Описывается как карта маршрутов с указанием, какой роли маршрут доступен:

```
/login                        OTP: телефон → код → ошибки (неверный / истёк / много попыток / номер не найден)
/role                         выбор роли при первом входе, если ролей две
/c                            кабинет клиента  (/c/home, /c/documents, /c/limit, /c/help)
/s                            кабинет поставщика (/s/home, /s/documents, /s/referral, /s/clients, /s/offer)
/closed, /not-found           терминальные экраны
```

Переключение ролей — «бесшовное»: переключатель в шапке (сегмент «Клиент | Поставщик») виден только `dual`; переключение меняет префикс маршрута и сохраняет язык и сессию; последняя выбранная роль запоминается. Навигация внизу экрана на мобильных (4–5 пунктов), боковая — на десктопе; контакты поддержки и переключатель языка — в каждой оболочке. Здесь же — правила «на чьей стороне шаг» и компонент шкалы прогресса (клиент: Документы → Проверка → Решение → Подписание → Лимит активен; поставщик: Документы → Проверка → Активен), включая дозапрос документов (решено: шкала не откатывается, на текущем шаге появляется метка «нужны ещё документы» — это снимает демотивацию и не ломает линейную модель).

#### Сущности и статусы — `01-entities.md` + `01-statuses.md`

Сущности из требований описываются YAML-блоками, которые один в один переносятся в `src/entities/*/model/types.ts` и в генератор фикстур:

### 3.1 Анализ стека и архитектура, устойчивая к агентам ⚖️

**Сравнение вариантов** (критерии: статическая сборка под произвольный базовый путь для витрины, RTL/i18n, PWA, перенос в GitLab, минимум кода, который агенты знают плохо):

| Вариант | Статика под `/p/tadum/vN/` | PWA | Привязка к Cloudflare | Знание у агентов | Вердикт |
|---|---|---|---|---|---|
| **Vite + React + TanStack Router (SPA)** | Тривиально: `vite build --base` + `basepath` роутера | vite-plugin-pwa, зрелый | Нет: чистый `dist/` | Хорошее; типизированные маршруты дают ошибки компиляции вместо тихих поломок | **Рекомендую** |
| React Router v7/v8 framework mode (`ssr: false`) | Возможно через `basename`, но тянет конвейер framework mode | Да | Низкая | Большой, но устаревший корпус (v6 / `react-router-dom`), агенты путаются | Запасной |
| TanStack Start (SPA mode) | Рассчитан на опциональный сервер, базовый путь документирован слабо | Да | Средняя | Среднее | Нет — лишний сервер |
| Next.js + OpenNext | Воркер, не статика; Cloudflare сам теперь советует экспериментальный vinext | Через адаптер | Высокая | Отличное, но App Router/RSC в статическом режиме — источник ошибок | Нет |

**Рекомендация:** Vite 7/8 (мажор зафиксировать) + React 19 + TypeScript strict + **TanStack Router** (файловые маршруты, `routeTree.gen.ts`, типизированные `search`/`params`) + **TanStack Query** как единственный слой данных + shadcn/ui (Radix) + Tailwind v4 + react-i18next + vite-plugin-pwa + Wrangler (static assets, `not_found_handling: single-page-application`). Готовый стартер не брать: ни один не сочетает i18n + PWA + базовый путь + Cloudflare; собственный тонкий скелет агентам проще уважать. Структуру позаимствовать у `satnaing/shadcn-admin` (Vite + TanStack Router + shadcn, с RTL) и `alan2207/bulletproof-react` (границы модулей, ESLint).

**Архитектура «FSD-lite»** — слои `app / pages / widgets / features / entities / shared`, каждый срез экспортирует только `index.ts`:

```
src/
  app/            провайдеры, роутер, i18n, тема, PWA-регистрация
  pages/          один файл на маршрут (TanStack file-based)
  widgets/        составные блоки: шапка кабинета, шкала прогресса, карточка документа
  features/       действия пользователя: upload-document, switch-role, request-otp, copy-referral
  entities/       application, document, limit, supplier, referred-client (типы, маппинг статусов, UI-атомы)
  shared/
    ui/           компоненты shadcn (генерируются CLI, редактируются только через «владельца дизайн-системы»)
    api/          ports/ (интерфейсы репозиториев), adapters/mock, adapters/http (позже), fixtures/
    i18n/         ar/*.json, en/*.json, типы ключей, форматтеры Intl
    analytics/    словарь событий, track()
    lib/          утилиты
    config/       env, базовый путь, флаги демо-режима
```

Механическое соблюдение границ (а не просьбы в CLAUDE.md): `eslint-plugin-boundaries` (нижние слои не импортируют верхние), `dependency-cruiser` (циклы, граф в репозитории), `knip` (мёртвые экспорты), `jscpd` (дубли), TS `noUncheckedIndexedAccess`, отдельный CI-шаг `tsc --noEmit`. Файлы, которые агент не должен трогать без явного разрешения (токены, lock-файлы, CI, wrangler, `shared/api/ports`), защищены и deny-правилами в `.claude/settings.json`, и PreToolUse-хуком.

**Результат:** ADR-001 «Стек и архитектура» в `05 Разработка/ADR/`, раздел мастер-промпта.

### 3.2 Подключение shadcn и дизайн-система

Факты, которые меняют план (проверить на момент инициализации): с июля 2026 shadcn по умолчанию ставит Base UI, Radix остаётся полностью поддерживаемым — инициализируем явно `shadcn init -t vite -b radix --rtl`; с января 2026 у shadcn есть официальная поддержка RTL (`rtl: true` в `components.json`, CLI сам переписывает классы на логические `ms-/me-/start-/end-`, компонент `Direction`), что снимает большую часть риска арабского интерфейса; Calendar, Pagination и Sidebar требуют ручной проверки; у `tw-animate-css` есть известная ошибка с логическими slide-анимациями — лечится `dir="rtl"` на порталах (Popover/Select/Sheet).

Порядок работ:

1. **Пресет shadcn** (D-077, заменяет D-060): Кирилл настраивает в конструкторе тем shadcn базовую темизацию и систему токенов (палитра светлой и тёмной темы, радиусы, шрифт, стиль) и передаёт пресет агенту вместе с мастер-промптом; агент применяет его без изменений и добавляет поверх семантические токены Tadum (статусы, прогресс лимита, движение). Фиксация — `02 Дизайн-система и бренд/02-design-system.md`. Настроение при настройке пресета — «спокойный персональный менеджер», доверие, без «кредитной» агрессии.
2. **Токены** — `src/styles/tokens.css` (CSS-переменные в oklch; светлая и тёмная темы обе в MVP стандартным механизмом shadcn: класс `.dark` на `<html>`, провайдер темы с выбором «системная / светлая / тёмная», выбор хранится рядом с языком; каждая история Storybook и каждый скриншот — в обеих темах): цвета (бренд, статусы `pending / received / rejected / approved`, нейтрали), радиусы, тени, отступы, типографика двух письменностей (размерная шкала AR и EN различается: арабский текст требует больший `line-height`), контрольные точки.
3. **Шрифты** (решено): **Geist** для английского (идёт с shadcn, OFL) и **IBM Plex Sans Arabic** для арабского — заголовки и текст одним семейством (OFL). Geist не содержит арабских глифов, поэтому `font-family` задаётся по `lang`: `:lang(ar) { font-family: "IBM Plex Sans Arabic", "Geist", sans-serif }`, латиница внутри арабского текста (номера, SAR) берётся из Geist через каскад. Самостоятельный хостинг через fontsource (woff2, начертания 400/500/600/700), предзагрузка основного начертания текущего языка, `font-display: swap`, шрифты в прекэше PWA. Cosmic Octo, Lalezar и Be Vietnam Pro из исходных требований не используются — отразить в `01-nfr-locale-brand.md`.
4. **Компоненты**: базовый набор shadcn (Button, Input, OTP Input, Card, Badge, Progress, Tabs, Sheet, Dialog, Dropdown, Toast/Sonner, Skeleton, Alert, Accordion, Table) + проектные композиты в `widgets/`: `StatusTimeline`, `NextStepCard`, `DocumentCard` (все статусы), `UploadDropzone` с прогрессом и предвалидацией, `LimitGauge`, `ChecklistItem`, `ReferralCard` с QR, `SupportBar`, `LanguageSwitch`, `RoleSwitch`.
5. **Storybook 10** как живая документация дизайн-системы: история на каждое состояние, обязательно в AR-RTL и EN-LTR (глобальный переключатель `dir`), аддон a11y, интеграционные тесты через Vitest-аддон.
6. **Владелец дизайн-системы** — правило `.claude/rules/design-system.md` (сырые hex/px запрещены, только токены и примитивы shadcn, новые компоненты — только через `shadcn add` или ревью) + субагент `design-system-reviewer` (см. 3.7).

**Результат:** `02-design-system.md` (пресет и токены Tadum, зеркало `tokens.css`), Storybook в репозитории, ADR-002 «Дизайн-система».

### 3.3 Mobile-first, PWA, кроссбраузерность

- **Mobile-first**: стили пишутся от 360 px вверх; десктоп — расширение (боковая навигация, двухколоночные списки). Цели касания ≥ 44 px, нижняя навигация, безопасные зоны iOS (`env(safe-area-inset-*)`), `100dvh` вместо `100vh`.
- **PWA**: `vite-plugin-pwa` в режиме `generateSW`, `registerType: 'autoUpdate'`, прекэш оболочки и шрифтов, `NetworkFirst` для будущего `/api/`; манифест с `dir: rtl`, `lang: ar`, иконками `any` и `maskable`, `apple-touch-icon`. На iOS нет `beforeinstallprompt` — показываем инструкцию «Поделиться → На экран “Домой”». Локальные данные считаем кэшем, не хранилищем (WebKit удаляет данные сайта после 7 дней без использования). Каждая версия на витрине имеет свой `scope` (`/p/tadum/vN/`) — это удобно: версии не мешают друг другу.
- **Встроенный браузер WhatsApp**: отдельный проход тестирования; скачивание файлов — только прямыми ссылками, без `blob:`; подсказка «Открыть в браузере» при детекции IAB; не полагаться на всплывающие окна.
- **Кроссбраузерность**: Playwright-проекты `iphone-safari`, `android-chrome`, `desktop-chrome`, `desktop-safari`, `desktop-edge`; матрица в DoD. `browserslist` = две последние версии перечисленных.
- **i18n-форматирование**: единый модуль `shared/i18n/format.ts` (`formatMoney`, `formatDate`, `formatPhone`); прямые вызовы `toLocaleString` запрещены линтером.

**Результат:** раздел мастер-промпта, `playwright.config.ts` с проектами, чек-лист PWA в DoD.

### 3.4 Витрина Proto: публикация версий Tadum

Как устроена витрина (из кода воркера `proto`): статический сайт с реестром `registry.json`; каждый прототип — запись `{ slug, title, versions: [{ version: "v1", status, routing: "history" }], defaultVersion, separatePassword }`; сборки лежат под `/p/{slug}/{vN}/`; `/p/{slug}/latest/` перенаправляет на последнюю не-draft версию; при `routing: "history"` воркер сам отдаёт `index.html` на вложенные пути (SPA-фолбэк внутри версии уже реализован — отдельного кода не нужно); вход — общий пароль сайта (`SITE_PASSWORD`), а для прототипов с `separatePassword: true` — дополнительный пароль из секрета `PROTOTYPE_PASSWORDS` (JSON `{ "slug": "пароль" }`), сессия 14 дней в cookie `proto_session_{slug}`; превью — `/_previews/{slug}.{png|jpg}`.

Что сделать для Tadum (в репозитории Proto и в Cloudflare):

1. Добавить в `registry.json` запись `slug: "tadum"`, `title: "Tadum — кабинеты клиента и поставщика"`, `separatePassword: true`, версии по мере выпуска; превью-картинка.
2. Добавить пароль в секрет: `wrangler secret put PROTOTYPE_PASSWORDS` со значением JSON, где к существующим записям добавлен `"tadum": "<пароль>"`. Зрителю понадобятся два пароля: общий от витрины и от Tadum — отразить в инструкции для команды в `06 Версии прототипа/`.
3. Публикация версии — **ровно тот же процесс, что у прототипа «Единая активация»** (решено, D-019): вы говорите Claude Code (веб-версия, D-076) «опубликуй vN», он собирает Tadum с `--base=/p/tadum/vN/` (и `basepath` роутера из `import.meta.env.BASE_URL`), кладёт сборку в Proto в `p/tadum/vN/`, дописывает версию в `registry.json`, коммитит в `main` Proto и деплоит витрину — без PR и кнопки merge. Команда `pnpm release:proto vN` в репозитории Tadum — только обёртка над тем механизмом, который уже есть в Proto. При написании мастер-промпта (сессия 9) взять этот механизм из репозитория Proto (скрипты, README, как публиковалась «Единая активация») и повторить его для slug `tadum` один в один, ничего не изобретая. Публикация версии — отдельное решение «пора показать команде», а не следствие merge PR в Tadum: одна версия на витрине = несколько смерженных PR.
4. **Демо-режим** в сборке для витрины: плавающая панель (скрыта в проде), где можно выбрать персону (клиент на сборе документов / с отклонённым документом / на проверке / одобрен / закрыт; поставщик новый / активный; двойная роль), язык и состояние сети — так команда смотрит любой сценарий без бэкенда. Состояние персоны хранится в URL (`?persona=`), чтобы ссылку на конкретное состояние можно было отправить в чат.
5. Release notes на каждую версию — `06 Версии прототипа/vN.md` (что смотреть, какие сценарии, известные ограничения, ссылка `https://proto.kirillgloba.workers.dev/p/tadum/vN/`).

Репозитории (решено): Tadum живёт в отдельном репозитории в вашем GitHub (рядом с Proto, независимо от него) и уезжает в GitLab команды только на этапе передачи; Proto остаётся в вашем GitHub навсегда и только принимает готовые сборки. Публикация запускается там же, где и для «Единой активации», — в облачной сессии Claude Code (веб-версия) с той же конфигурацией, что у «Единой активации» (D-076): доступ к обоим репозиториям и к Cloudflare. Подтверждения Кирилла перед push и деплоем заложены в сам скрипт публикации.

**Результат:** запись в реестре, пароль, скрипт релиза, инструкция для зрителей.

### 3.5 Без бэкенда: данные, адаптеры, перенос в GitLab

**Порты и адаптеры.** В `shared/api/ports/` — интерфейсы `AuthRepository`, `ApplicationRepository`, `DocumentRepository`, `LimitRepository`, `SupplierRepository`, `ReferredClientsRepository` с типами из `01-entities.md` и схемами Zod. Сейчас единственная реализация — `MockAdapter`: детерминированные сиды (`faker` с фиксированным seed), состояние в памяти + `localStorage` для демо, настраиваемая задержка и инъекция ошибок, переходы статусов по правилам из `01-statuses.md` (например, «отправил комплект → `under_review`», «загрузил отклонённый → `received`»). Позже команда пишет `HttpAdapter` (по OpenAPI-контракту API над Odoo — сгенерировать клиент `openapi-ts`) и меняет один env-флаг. MSW — только в тестах, когда появится `HttpAdapter`. Фикстуры-персоны лежат в `shared/api/fixtures/personas/*.ts` и используются и демо-режимом, и Playwright.

**Контракт для будущего бэкенда.** Документ `05 Разработка/05-backend-contract.md`: перечень портов с сигнатурами, предполагаемый маппинг на модели Odoo (crm.lead, Doc Collection Engine, tadum.supplier), что именно должен отдавать API, чтобы фронтенд не менялся. Это главный подарок команде GitLab.

**Перенос GitHub → GitLab (чек-лист, выполняется заранее, а не в день переезда):**

- в коде нет ничего GitHub-специфичного: деплой — `wrangler deploy`, одинаковый в GitHub Actions и GitLab CI (Cloudflare документирует оба); секреты только `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`;
- `.github/workflows/ci.yml` и зеркальный `.gitlab-ci.yml` держим оба с первого дня (jobs одинаковые: `install → typecheck → lint → test → build → e2e → size`); так переезд — это `git push` на новый remote;
- Claude Code-слой (`.claude/`, `CLAUDE.md`, хуки) не зависит от хостинга; GitHub Action `claude-code-action` — единственная потеря, в GitLab её заменит запуск `/code-review` в сессии Claude Code;
- Issues экспортируются в GitLab импортом; брифы фич всё равно лежат в Drive;
- `pnpm` с зафиксированной версией в `packageManager`, `.nvmrc`, `CONTRIBUTING.md` с полной инструкцией запуска без Claude (команда может не использовать его).

**Результат:** `05-backend-contract.md`, `05-migration-to-gitlab.md`, оба CI-файла в репозитории.

### 3.7 Оркестрация: агенты, скиллы, хуки, MCP, плагины

Принцип разделения (по документации Claude Code): **факты и инварианты** → `CLAUDE.md` и `.claude/rules/*.md` (с `paths:` для точечной загрузки); **процедуры** → скиллы `.claude/skills/*/SKILL.md` (они же слэш-команды); **изолированное суждение с ограниченными инструментами** → субагенты `.claude/agents/*.md`; **запреты** → `permissions.deny` + хуки.

#### Рабочий цикл фичи

`/feature-brief <id>` (создать бриф из шаблона, положить в Drive и issue) → `/plan <id>` (план в plan mode, согласование) → реализация в worktree одной фичи → `/verify` (typecheck, lint, тесты, Storybook, Playwright AR+EN, скриншоты) → `/design-review`, `/rtl-qa`, `/ux-copy-review` по необходимости → `/pr` (описание по шаблону DoD, changeset) → Code review в GitHub (`claude-code-action`) → merge → `/release-proto vN` по накоплению.

### 3.8 Требования к готовому PR (Definition of Done)

Полный чек-лист — отдельный шаблон `05 Разработка/Шаблоны/Definition of Done для PR.md` ([Drive](https://drive.google.com/file/d/1Khr1JkbcTTGnmzJw9fGlQmx3r-noZi8X/view)); он же станет `.github/PULL_REQUEST_TEMPLATE.md`. Кратко, что проверяется и чем:

| Группа | Проверка | Автоматика |
|---|---|---|
| Соответствие | PR ссылается на бриф `TD-###` и сценарии; критерии приёмки отмечены | шаблон PR, ревью |
| Состояния | loading / empty / error / offline / blocked / длинный арабский текст — есть в Storybook | Storybook-тесты |
| Адаптивность | 360 / 768 / 1280, без горизонтальной прокрутки, цели ≥ 44 px | Playwright-скриншоты |
| RTL/LTR | скриншоты обеих направленностей, нет физических классов, иконки зеркалятся только направленные | ESLint-правило + grep, скриншоты |
| i18n | нет строк в коде, ключи в `ar` и `en`, формы множественного числа, форматтеры | `i18next-parser --fail-on-warnings`, lint |
| Дизайн-система | только токены и примитивы, новые компоненты согласованы | `design-system-owner`, lint на hex/px |
| Доступность | axe без ошибок на уровне AA, клавиатура, фокус, подписи | `@axe-core/playwright` |
| Аналитика | события из брифа вызываются на успехе и ошибке | unit-тест на `track` |
| Данные | изменения только через порты; моки обновлены; персоны демо работают | typecheck, тесты адаптера |
| Качество кода | `tsc`, ESLint, границы слоёв, нет мёртвого кода, нет дублей | CI: typecheck, lint, dependency-cruiser, knip, jscpd |
| Размер | бюджет первого чанка, Lighthouse на `main` (perf ≥ 90, a11y = 100, PWA installable) | size-limit, Lighthouse CI |
| Браузеры | smoke в iOS Safari / Android Chrome профилях | Playwright-проекты |
| Релиз | changeset, release notes при публикации версии | changesets |
| Безопасность | нет PII в URL/логах/аналитике, секреты не в коде | secret scan, ревью |

CI (GitHub Actions и зеркало GitLab): `install → typecheck → lint (ESLint + границы + rtl + i18n) → unit/Storybook → build → e2e + axe + скриншоты (ar, en) → size-limit`; Lighthouse CI — на `main` и ночью. Обязательные проверки на `main`, ветка защищена, squash-merge, Conventional Commits через commitlint.

### 3.9 Мастер-промпт для создания среды — структура

Документ `05 Разработка/05-master-prompt.md` пишется после утверждения этого плана и состоит из блоков, каждый из которых агент выполняет и проверяет отдельно (чтобы можно было остановиться и продолжить):

2. Инициализация: `pnpm create cloudflare --framework=react` или чистый Vite → TanStack Router → `shadcn init -t vite -b radix --rtl` → Tailwind v4 → i18n → PWA; версии зафиксированы.
3. Структура слоёв и правила границ; создание пустых срезов с `index.ts`.
4. Дизайн-система: токены, шрифты, базовые компоненты, Storybook с переключателем RTL.
5. Порты, `MockAdapter`, персоны.
6. Оболочка кабинета, маршруты, переключение ролей и языка, демо-панель.
7. Качество: ESLint-конфиг, хуки, CI в двух вариантах, DoD-шаблон, changesets.
8. Слой Claude Code: `CLAUDE.md` (< 200 строк, ссылки вместо текста), `rules/`, агенты, скиллы, `.mcp.json`, `settings.json`.
9. Публикация v1 на витрину тем же механизмом, что «Единая активация» (взять из репозитория Proto и обернуть в `pnpm release:proto`), и запись в `06 Версии прототипа/v1.md`.
10. Критерии приёмки среды: `pnpm verify` зелёный, Storybook открывается в AR и EN, витрина показывает v1 по паролю, хук блокирует правку токенов, агент `rtl-qa` находит специально внесённый `ml-4`.

## 6. Риски и как их снижаем

| Риск | Снижение |
|---|---|
| Агенты «переписывают» ранее сделанное | Границы слоёв в линтере, защищённые пути в deny-правилах и хуках, маленькие PR, Writer/Reviewer, worktree на фичу, `pnpm verify` на Stop |
| Арабская вёрстка ломается незаметно | `rtl: true` shadcn, lint на физические классы, скриншоты AR в каждом PR, агент `rtl-qa`, порталы с `dir` |
| Прототип расходится с будущим бэкендом | Порты с Zod-схемами, контракт для бэкенда, маппинг на Odoo в документе, моки с реальными переходами статусов |
| Быстрая эволюция инструментов (Vite 8, shadcn Base UI, TanStack) | Мажоры зафиксированы, Renovate с ручным одобрением мажоров, Context7 вместо памяти модели, ADR на каждое отступление |
| Документация расходится между Drive и репозиторием | Односторонняя синхронизация, запрет правок снимка, дата источника в шапке |
| Встроенный браузер WhatsApp ведёт себя иначе | Отдельный профиль тестирования, прямые ссылки на файлы, подсказка «открыть в браузере» |
| Арабский текст попадает в системный шрифт (Geist без арабицы) | `font-family` по `:lang(ar)`, предзагрузка IBM Plex Sans Arabic, проверка скриншотов AR в обеих темах |
